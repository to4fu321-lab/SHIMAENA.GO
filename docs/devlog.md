## 11/7 「声でない」を直す（本人の指摘）
- 確かめたこと: 本番の `/api/voice` は mp3 を返していた（サーバーは正常）。なのに本番の記録には、スマホからの `/api/voice` が1件もなかった → 画面が声を取りに行く前に止まっていた。
- 原因: 声を Web Audio（効果音と同じ音の入れ物）で鳴らしていた。入れ物が動いていないと取りに行かずにブラウザの声へ回るが、iPhone はタップから時間がたつとブラウザの読み上げを鳴らさない。さらに iPhone はマナーモード（消音スイッチ）だと Web Audio の音を消す。
- やったこと: 声は画面に1つの `<audio>` で鳴らす（マナーモードでも鳴る）。🔊 を押したタップの中で、無音を一度鳴らしてブラウザの読み上げにも一度話させ、あとから鳴らせるようにする（`primeCaptainVoice`）。オンのまま開き直したときは、画面の最初のタップで同じことをする。自動再生を制限した Chromium で、🔊 → 声が鳴り始める、オンのまま開き直して文を送る → 返事が声で鳴る、を確かめた。
- 次: 本人の iPhone で、マナーモードのままでも 🔊 で声が出るかを見てもらう。それでも出ないときは、音量ボタンと、ほかのアプリが音を使っていないかを見る。

## 11/7 「機械音しか出ない」「最初に話したことを読む」を直す（本人の指摘）
- 確かめたこと: 本番の `/api/voice` は続けて4回頼んでも毎回声を返した（2〜4秒）。一度作った声は CDN が分けた頼み方（Range）に 206 で答えるが、新しい文の声はサーバーが毎回作るので、分けた頼み方に答えていなかった。
- 原因①（機械音）: iPhone の Safari は `<audio>` にサーバーの URL を渡すと、ファイルを少しずつ分けて取りに行く。隊長の返事は毎回新しい文なので答えられず、再生をあきらめてブラウザの声に回っていた（と考えられる。この環境に WebKit がないので実機では未確認）。
- 原因②（最初の文）: 文を送ると仮の吹き出し（tmp-…）が出て、返事で消える。「どこまで読んだか」をその id で持っていたので見失い、流れの最初から読んでいた（声は前から 200 字なので、最初に話したことが読まれた）。
- やったこと: ①声の mp3 は fetch で丸ごと受け取り、端末の中の URL（blob）で `<audio>` に渡す。`/api/voice` も分けた頼み方に 206 で答える。②「すでに見た隊長の吹き出しの id」を覚えて、新しく届いた分だけを読む（`lib/chat/speak.ts`、テスト3本）。③声の途中で画面をタップすると、無音の鳴らし直しで声が止まることがあった → 中断（AbortError）は「鳴らせた」と同じに扱い、鳴っている間は鳴らし直さない。
- 次: 本人の iPhone で、🔊 → 隊長の声、文を送る → 新しい返事だけが声で読まれるかを見てもらう。

## 11/7 返事を読まない・自分の文がしばらく出ない・「隊長が調べた」・声のアイコン（本人の指摘4つ）
- 確かめたこと（本番・iPhone の画面サイズ）: 文を送ってから自分の吹き出しは 0.08 秒で出た。隊長の返事は約 23 秒（鍵ありのエージェント）、その返事の声ができるまでさらに約 10 秒（鍵なしの VOICEVOX は長い文ほど遅い。サーバーは 12 秒であきらめていた）。
