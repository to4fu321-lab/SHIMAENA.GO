# 第二案：縫製のラクスル（仮称: ぬいしょ）— 検討メモ（11/2 時点、未確定）

> ハッカソン期間中の検討記録。登場人物・社名はすべて架空。

## 本人の原案
日本の若いデザイナーが仕立てた衣類を、ラクスル（印刷工場の空き稼働を束ねるモデル）のように **国内縫製工場の量産レーンに乗せられる** プラットフォーム。第一案より難易度は高い、と本人も認識。

## 前提として知っておくべき事実（調査済み）
- **既存プレイヤーがいる**: シタテル（熊本、2014年創業）が同じ構図で、2025/11 時点で縫製工場・生地メーカー 5,300社超、ブランド 約24,700社が登録、同月に資金調達を発表。他に nutte（個人と縫製職人のマッチング）など。
  → 「工場とデザイナーをつなぐ」だけでは審査員に「シタテルと何が違う？」と聞かれる。**差別化は Claude で何を自動化するか**に置く必要がある。
- **業界の痛み**は本物: 小ロットは1枚単価が跳ね上がる／工場は空き稼働が埋まらない／工賃が最低賃金上昇に追随しない（経産省2017年調査で65%の工場が「引き上げてもらえず」）／縫製業は技能実習生の労基法違反事案の大部分を占める（岐阜労働局）／国産比率は3%未満。
- ラクスルが成立したのは **印刷が規格化できる**から（サイズ・紙・部数）。縫製は1点ごとに仕様が違うので規格化できず、だから人力コンシェルジュ（シタテル）が必要になる。**ここが Claude の出番**: 規格化できないものを、AIが「仕様書・工程・見積」に翻訳する。

## 6日で成立させるための絞り込み（提案）
マーケットプレイス全部は作らない。**「デザイナーの言葉と絵」⇄「工場の仕様書・工程・工賃」の翻訳機** を中核にし、工場マッチングはモックデータで見せる。

| 要素 | 内容 |
|---|---|
| 主人公 | 東京の26歳デザイナー（架空）。初コレクションのシャツ30枚を作りたいが、工場に電話しても「ロットが少ない」「仕様書がないと見積もれない」と断られ続ける。もう一人の主人公は岐阜の縫製工場の2代目（架空）。1月〜2月のレーンが空いているが、営業する人手がない |
| 依頼側の体験 | スケッチ写真＋話し言葉（「オーバーサイズのシャツ、前立て隠し、袖は少し長め」）を投げる → Claude が **縫製仕様書（テックパック）の草案**、**工程分解（裁断・芯貼り・前立て・衿・袖・脇・裾・ボタンホール…）と標準工数**、**工賃レンジと生地・付属リスト**、**30枚ロットでの現実的な単価** を返す。足りない情報は Claude が質問で埋める（「裏地は？」「ボタンは貝？」） |
| 工場側の体験 | 空きレーン（週×人数）を登録。Claude が仕様書を読み、その工場の得意工程と空きに合う案件を提示。**作業指示を多言語化**（ベトナム語・中国語など。技能実習生・特定技能の現場向け）。「この前立ての縫い方は当工場では〇〇」と工場の流儀を仕様書に反映 |
| 継承（テーマ1の核心） | 工場のベテランに Claude がインタビュー形式で「この工程のコツ」を聞き取り、**工程ごとの職人ノウハウ**として仕様書に紐づけて蓄積。人が辞めても工場の「縫い方」が残る |
| マッチング | 10社程度の架空工場 DB（得意工程・空き・工賃水準・所在地）。Claude がスコア付きで3社提示し、理由を日本語で説明 |
| 見せ方 | スケッチ1枚が、数十秒で「工場が見積もれる紙」に変わる瞬間がデモの山場 |

## Claude の使いどころ
1. **画像＋話し言葉 → 構造化仕様書（JSON）**。曖昧さを質問で解消する対話型
2. **工程分解と工数推定**（採点表＝標準工程テーブルを渡して毎回同じ基準で）
3. **工場ごとの流儀を反映**した仕様書の書き換え（工場プロファイルをコンテキストに）
4. **多言語の作業指示書**生成（現場の実習生向け。図解は既存のスケッチを引用）
5. **ベテランへのインタビュー・エージェント**（音声→文字→工程ノウハウとして整理）
6. 開発側: Skills（仕様書テンプレ／工程テーブル更新）、サブエージェント（依頼側UI・工場側UI並行）、フック

## リスク
- **ドメインの正確さ**: 縫製の工程名・工数・工賃相場を知らないと、仕様書が「それっぽいだけ」になる。深さ20%とインパクト30%の「現場から出発しているか」で減点されうる。**本人または近い人に縫製の知見・工場の知り合いがあるかで、この案の勝率が大きく変わる**
- **既存サービスとの比較**を必ず README とデモ冒頭で先回りする（「シタテルの人力コンシェルジュ部分を、誰でも使えるAIにした」）
- 二者（依頼側・工場側）の画面が要るので実装量は第一案の1.5倍程度。6日・初心者だと「翻訳機」単体に落とす判断が11/5までに要る
- 禁止例の「画像解析ツール」に見えないよう、画像はあくまで入口。主役は仕様書・工程・継承

### B-4. ヒアリング項目（工場／デザイナー）
**工場に**
- 小ロットを断る本当の理由は（段取り替え・工賃・仕様書の不備・納期）？
- 見積に最低限必要な情報は何か？ 仕様書のどこが抜けていると困るか？
- シャツ1枚の工程をざっくり何工程・何分で見ているか？ 工賃はどう決めるか？
- 外国人スタッフへの指示はどうしている？ 言葉で困る場面は？
- ベテランしか知らない「コツ」はどこに残っている（紙・頭の中・動画）？
- 空きレーンはいつ、どれくらい出るか？ 埋められるなら何枚からなら受けるか？
**デザイナーに**
- 工場探しで何件断られた？ 断り文句は？
- 仕様書を自分で書けるか？ 何が書けないか？
- いくらなら30枚を頼むか？

### B-5. 最大のリスクと保険
- ドメインの誤り → ヒアリングで工程テーブルを一度検証してもらう。README に「〇〇工場の協力で検証」と書ければ深さの加点
- シタテルとの比較 → デモ冒頭と README に「人力コンシェルジュの部分を AI にして、誰でも・即日・無料で使えるようにした」と先回り
- 実装量 → 11/5 の通し確認で、工場側のインタビュー機能を削る判断
- デモの地味さ → 山場は「スケッチが30秒で仕様書になる」の1カット。ここに演出を集中
