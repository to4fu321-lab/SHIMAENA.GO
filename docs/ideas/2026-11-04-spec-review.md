## 1. 🔴 すぐ直す（食い違い・動かない恐れ）

### 1-1. 週の区切りが2つある
- 5章: 「週＝日〜土」（得点・称号の集計 `lib/game/week.ts` もこの通り）
- T48: 「チームの期間は月曜〜日曜、日曜の夜 21:00 に組み直し」（`lib/team-theme.ts`）
- 起きること: 日曜の朝の得点が「新しい週」に入るのに、チームはまだ「前の週」のまま。日曜の夜の実況は、その日の朝の分を数えない恐れがある。
- **案**: どちらも**月〜日**にそろえる（日曜の夜に締めて、実況とシャッフル）。5章を書き換え、`weekStart` を月曜始まりに。

### 1-2. 6:40 の作戦を起こすものがない
- 11章: 「Cron: 21:00 予告、6:30 点呼、6:40 作戦」
- 実際の `vercel.json`: 21:00 と 6:30 の **2本だけ**（Vercel の Hobby プランは1日2本まで）。6:40 の作戦は「6:40 以降に誰かが点呼に答えたとき」に動く（`planIfDue`）。
- 起きること: 6:40 以降に誰も答えなければ、**作戦が配信されない**（人手不足のヘルプ通知も出ない）。
- **案（どれか1つを本人が選ぶ）**:
  - A. 6:30 の Cron で点呼を送ったあと、同じ処理の中で 10分待ってから作戦を出す（Vercel の関数の最大実行時間の確認が要る）
  - B. 外の無料の定期実行（GitHub Actions の schedule など）で 6:40 に `/api/cron/plan` を叩く
  - C. 点呼の締めを「全員が答えたら、または 6:40 以降の最初の操作で」と仕様に書き、デモは `/admin` のボタンで進める（今の動き）
- デモだけなら C で足りるが、仕様に**正直に書く**。

### 1-3. LINE のないお年寄り（家族の代理登録）が毎回「返事なし」になる
- 1章: LINE が使えなければ家族が代理登録。
- 実際: 点呼は LINE のある人にだけ届く。代理登録だけのお年寄りは答えられないので、**雪の朝のたびに「返事なし」→ 灰色点滅 → 近所に声かけ → 家族に通知**になる。
- **案（本人の判断が要る）**:
  - A. 点呼を**紐づいた家族に**送り、家族が代わりに答えられる（「お母さんは今朝、外に出られそうですか？」）
  - B. 代理登録の家は「いつも来てほしい」（点呼なしで毎回ミッション）にする
  - C. 今のまま（毎回見守り）。ただし家族への通知は「返事がない」ではなく「今朝も見守りに行きます」の文にする
- おすすめは **A**（家族も参加者になる。コンシェルジュの「遠くの家族」とつながる）。

## 2. 🟡 もっと具体的にしないといけない所

### 2-1. LINE の通数（月の上限と、足りないときの順番）
- 仕様に通数の記述がない。コードのコメントに「無料プランはプッシュ月 200 通」。
- 雪の朝1回で、1人に 予告1＋点呼1＋作戦1＝**3通**。人手不足のヘルプ通知・家族への通知・カードが加わる。10人×雪の朝7回で上限に届く。
- **書くこと**: ①1人1回の雪の朝で送る最大通数 ②上限に近いときに削る順番（例: カードの画像 → 予告 → …、点呼と作戦と見守りは最後まで削らない）③返信（reply、無料）で済ませる所の一覧 ④本番で使う LINE のプラン（本人が確認）。

### 2-2. 個人情報の扱い（同意・保存期間・消し方）
- 12章は「入れない・出さない」だけ。実際の利用者のために足りないもの:
  - **同意**: 登録の最初に「家の位置は、雪かきに行く人にだけ伝えます」の一文と「はい」ボタン。
  - **保存期間**: 完了写真（`photoUrl`）・点呼の答え・朝の記録をいつまで残すか（例: 写真は確認したら残さない、朝の記録は冬が終わるまで）。
  - **消し方**: LINE のブロック（unfollow）で何を消すか（今は登録途中の会話だけ消える）。`/settings` に「登録を消す」。
  - **見える範囲の表**: 名前・家の位置・拠点番号・写真を、誰が見られるか（本人／向かう人／家族／町内／公開ページ）を1つの表に。
- 地域のお年寄りを扱うので、審査の「深さ」で効く。

### 2-3. Claude の仕事の一覧（散らばっている）
- 9章（1〜5）、v1.1（6 実況）、v1.3（7〜9）、v1.6（番号なしで4つ）に分かれている。今は**14の仕事**がある。
- **書くこと**: 1つの表にする。列は「仕事／いつ呼ぶ／モデル（Opus・Haiku）／入力／出力（JSON の形）／確かめ方／失敗・キーなしのとき」。例:

| 仕事 | いつ | モデル | 失敗・キーなし |
|---|---|---|---|
| レベル判定 | 登録の最後 | Haiku | 採点表の計算 |
| 司令官 | 6:40 の作戦 | Opus | 計算の割り当て |
| 写真確認 | 完了写真 | Opus | 「報告として受け付け」 |
| ことばで答える | 点呼中の自由な文 | Opus | 言葉の一覧 |
| 隊長の一言 | 点呼の時に1回 | Haiku | 定型 |
| … | | | |

- あわせて、9-1 **レベル判定は計算で足りる**（採点表の規則どおり）。v1.6 の「ルールで書けることは普通のプログラム」と食い違う。→ 計算にするか、「判定の理由の一文だけ Claude」と書き直す。
- 5章「翌週のシャッフルは Claude が」→ 実際は計算（`lib/game/week.ts`）で、文だけ Claude。「体力でバランス」も、体力のデータはない（あるのは「朝は何分動ける」）。→ **「出撃回数と動ける分と方角で、計算でバランス」**に。

### 2-4. 文字とボタンの大きさの基準が2つある
- CLAUDE.md: 本文 **18px** 以上。T41: 本文 **16px** 以上・ボタン 56px 以上。
- **案**: 仕様に1行で決める（例: 本文 18px・補足 16px・ボタンの高さ 56px 以上・1画面のボタンは2つまで・390×844 と 375×667 でスクロールしない）。

### 2-5. 家族・サポーターの立場
- 家族: 紐づけ（`FamilyLink`）だけで、参加者の役割にはない。点呼（1-3）、応援スタンプ、コンシェルジュの「遠くの家族」を考えると、**家族ができること**を1つの表にしたい（受け取る通知／押せるボタン／見られるもの）。
- サポーター（町内会役員役）: 仕様は名前だけ。実際は環境変数 `SUPPORTER_LINE_USER_IDS`。→ 仕様の「環境変数」に書き、「サポーターは何をする人か（1km まで声をかけても足りない家の連絡を受ける）」を1行で。

### 2-6. 子どもの参加
- 0章: 「子どもは保護者と一緒に偵察・補給で参加」。→ 年齢を聞いていないので、アプリでは守れない。**「子どもは登録しない。保護者の登録で一緒に来てよい（チームの人数には数えない）」**のように、アプリが守れる形に書き直すか、文を消す。

### 2-7. 屋根・危ない作業
- `/rules` の安全に「屋根の下に近づかない」はあるが、仕様の3章（小タスク）に「**屋根の雪下ろし・脚立・除雪機はミッションにしない**」がない。Claude（司令官・コンシェルジュ・今朝の先生）が勧めないように、仕様と採点表に1行。

### 2-8. デモ3分（13章）が古い
- 今の台本は v1.1 の追記で継ぎ足し。T47〜T55（行き先カード・隊長カード・ことばで依頼・今朝の先生・招待文）が入っていない。「建物が塗られる」も 50m マスと食い違う。
- 審査は「デモ 25%」「Claude の活用 25%」。**Claude が人を動かした瞬間**を3つ選んで台本に入れる案:
  1. おばあちゃんが LINE に声で「9時までに玄関だけ」→ 地図とカードに「09:00 まで・玄関前」（ことばで依頼）
  2. 完了写真 → Claude の確認 → MISSION CLEAR（写真確認）
  3. 学生の行き先カードに「🎓 今朝の先生のコツ」→ 完了後の招待文で友だちへ（今朝の先生・招待文）
- 13章は「`docs/demo.md` が正本」とだけ書き、台本は demo.md に一本化する。
